UG 1 — Inyección de comandos en PowerShell
                                                                                                                                                                                                                                                  
  Severidad: CRÍTICA
  Archivo: src/main/services/restore.ts:12-15
  Tipo: Seguridad

  El código actual:
  const fullDescription = `${description} (${timestamp})`;
  await execa('powershell', [
      '-Command',
      `Checkpoint-Computer -Description "${fullDescription}" ...`
  ]);

  Qué pasa:
  Todo el comando de PowerShell se pasa como un solo string al argumento -Command. Dentro de ese string, fullDescription se interpola directamente entre comillas dobles. En PowerShell, las comillas dobles permiten la expansión de variables y 
  subexpresiones.

  Si description o timestamp contienen caracteres especiales como ", `, $(), o $(...), PowerShell los interpreta como código ejecutable. Por ejemplo, si un locale genera un timestamp como 14/02/2026, 7:00 "PM", las comillas rompen la
  sintaxis. Peor aún: un valor malicioso como "; Remove-Item C:\\ -Recurse -Force; " se ejecutaría como comando de sistema.

  Por qué es crítico:
  La app se ejecuta obligatoriamente como Administrador. Cualquier inyección se ejecuta con privilegios elevados, sin restricción.

  Impacto actual:
  Hoy el description viene hardcodeado como "All Updater Auto-Restore" desde App.tsx:156, así que el riesgo inmediato es bajo. Pero new Date().toLocaleString() en algunos locales puede generar strings con comillas, y si en el futuro el       
  description se vuelve configurable, es un vector de ataque directo.

  Cómo arreglarlo:
  Usar comillas simples de PowerShell (que no expanden) o escapear el string, o mejor aún, pasar el description como argumento separado y construir el comando de forma segura:
  // Opción segura: comillas simples de PowerShell (no expanden variables)
  `Checkpoint-Computer -Description '${fullDescription.replace(/'/g, "''")}' ...`

  BUG 2 — setupIPC() se ejecuta antes de app.whenReady()

  Severidad: CRÍTICA
  Archivo: electron/main.ts:100-116
  Tipo: Ciclo de vida / Inicialización

  El código actual:
  import { setupIPC } from '../src/main/ipc.js';
  setupIPC();                          // ← Línea 102: se ejecuta INMEDIATAMENTE

  app.whenReady().then(async () => {   // ← Línea 104: ready viene DESPUÉS
      // ...
      createWindow();
  });

  Qué pasa:
  setupIPC() en ipc.ts:10-16 crea instancias de todos los servicios:
  const historyService = new HistoryService();   // usa electron-store → necesita userData path
  const settingsService = new SettingsService();  // usa electron-store → necesita userData path
  const logger = new LoggerService();             // usa app.getPath('documents')

  electron-store internamente llama a app.getPath('userData') en su constructor. Según la documentación de Electron, app.getPath() no es confiable antes de que el evento ready se emita. En el main process de Electron, el app necesita
  inicializar su infraestructura interna primero.

  Además, en electron/main.ts:14-17, tú redefiniste userData para modo portable:
  if (app.isPackaged) {
      const portableDataPath = path.join(path.dirname(app.getPath('exe')), 'data');
      app.setPath('userData', portableDataPath);
  }

  Esto se ejecuta a nivel de módulo (antes de whenReady), pero setupIPC() también se ejecuta a nivel de módulo. El orden de ejecución depende del orden de las líneas, pero hay una race condition lógica: si electron-store cachea la ruta antes 
  de que setPath se ejecute, los datos se guardarían en la ruta equivocada.

  Impacto:
  - En desarrollo funciona por suerte porque el userData default existe
  - En producción portable, los settings y el historial podrían guardarse en una ubicación incorrecta o no encontrarse
  - Si Electron cambia el comportamiento de getPath pre-ready en futuras versiones, la app crashea al iniciar

  Cómo arreglarlo:
  Mover setupIPC() dentro de app.whenReady():
  app.whenReady().then(async () => {
      const isElevated = await ensureElevated();
      if (!isElevated) { /* ... */ }
      setupIPC();       // ← DESPUÉS de ready
      createWindow();
  });

  BUG 3 — Patrón frágil de cierre recursivo

  Severidad: MEDIA
  Archivo: electron/main.ts:50-68
  Tipo: Lógica / Estabilidad

  El código actual:
  win.on('close', (e) => {
      if (isOperationActive) {
          e.preventDefault();
          const choice = dialog.showMessageBoxSync(win!, { ... });
          if (choice === 1) {
              isOperationActive = false;
              win?.close();   // ← Esto RE-DISPARA el evento 'close'
          }
      }
  });

  Qué pasa:
  Cuando el usuario elige "Close Anyway", se pone isOperationActive = false y se llama win?.close(). Pero close() re-emite el evento close, así que el handler se ejecuta de nuevo. Funciona porque isOperationActive ya es false, así que la     
  segunda vez el if no entra y el cierre procede normalmente.

  Por qué es un problema:
  - Si alguien agrega lógica adicional al handler close fuera del if (por ejemplo, logging, cleanup, guardar estado), esa lógica se ejecutará dos veces
  - Es un patrón que confunde a cualquier desarrollador que lea el código, porque no es obvio que el cierre es intencionalmente recursivo
  - Si hay un bug que vuelve a poner isOperationActive = true entre el set y el close (por ejemplo, un IPC que llega justo en ese instante), el diálogo aparece de nuevo, creando un loop infinito de diálogos

  Cómo arreglarlo:
  Usar un flag explícito de "forzar cierre":
  let forceClose = false;

  win.on('close', (e) => {
      if (forceClose) return; // Dejar cerrar
      if (isOperationActive) {
          e.preventDefault();
          const choice = dialog.showMessageBoxSync(win!, { ... });
          if (choice === 1) {
              forceClose = true;
              win?.close();
          }
      }
  });

      await window.ipcRenderer.invoke('system:set-operation-active', true);  // ← Se activa

          } finally {

  Qué pasa:

  2. Se ejecuta system:set-operation-active(true) → en main process, isOperationActive = true
  3. El restore point falla (PowerShell error, timeout, permisos, etc.)
  4. Se muestra toast de error y se hace return
  5. Nunca se ejecuta system:set-operation-active(false)

  Cómo arreglarlo:
  Añadir cleanup antes del return:

      addToast(t('restoreFailedAbort'), "error");
      setIsCreatingRestore(false);
      setIsInstalling(false);          // ← Añadir
      setCurrentLogLine(null);

  <button

  BUG 9 — Memory leak: listener de winget:log nunca se remueve

  Severidad: MEDIA
  Archivo: src/App.tsx:43-51 + electron/preload.ts:7-10
  Tipo: Memory leak

  El código del preload:
  contextBridge.exposeInMainWorld('ipcRenderer', {
      on(...args: Parameters<typeof ipcRenderer.on>) {
          const [channel, listener] = args
          return ipcRenderer.on(channel, (event, ...args) => listener(event, ...args))
          //                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
          //                              Función anónima NUEVA — no es `listener`
      },
      off(...args: Parameters<typeof ipcRenderer.off>) {
          const [channel, listener] = args
          return ipcRenderer.off(channel, listener)
          //                              ^^^^^^^^
          //                              Intenta remover `listener` original
      },
  });

  El código del renderer:
  useEffect(() => {
      const handleLog = (_: any, log: string) => { ... };
      window.ipcRenderer.on('winget:log', handleLog);       // Registra wrapper anónimo
      return () => window.ipcRenderer.off('winget:log', handleLog);  // Intenta remover handleLog
  }, []);

  Qué pasa paso a paso:
  1. window.ipcRenderer.on('winget:log', handleLog) se llama
  2. Dentro del preload, se ejecuta ipcRenderer.on('winget:log', (event, ...args) => handleLog(event, ...args))
  3. Electron registra la función anónima wrapper, NO handleLog
  4. Cuando el componente se desmonta, se llama window.ipcRenderer.off('winget:log', handleLog)
  5. Dentro del preload, se ejecuta ipcRenderer.off('winget:log', handleLog)
  6. Electron busca handleLog en su lista de listeners del canal winget:log
  7. No lo encuentra porque lo que se registró fue el wrapper anónimo
  8. El listener permanece activo indefinidamente

  Impacto:
  Cada vez que el componente App se remonta (por ejemplo, con StrictMode en desarrollo, que monta/desmonta/remonta), se acumula un listener más. En producción con StrictMode habilitado, se duplica. Si la app tuviera navegación que
  desmonte/remonte App, los listeners se acumularían sin límite, y cada log de winget ejecutaría N callbacks en vez de 1.

  Cómo arreglarlo:
  Guardar la referencia al wrapper en el preload:
  on(channel: string, listener: (...args: any[]) => void) {
      const wrapper = (_event: any, ...args: any[]) => listener(...args);
      ipcRenderer.on(channel, wrapper);
      return wrapper; // Devolver para poder hacer off después
  },
  O más sencillo, pasar el listener directamente sin wrapper.
